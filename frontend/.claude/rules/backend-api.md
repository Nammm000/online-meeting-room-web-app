# Backend API Contract

The Spring Boot backend runs on port 8083 (`environment.apiUrl`, stateless JWT bearer auth). Every frontend service in `src/app/service/` maps 1:1 to a resource below; DTO interfaces in `src/app/model/` mirror the backend and document per-field quirks in doc comments.

- **Auth** (`AuthService`): `POST /auth/login` `{email, password}` → `{accessToken}` + HttpOnly refresh cookie; `POST /auth/signup` `{name, email, phone, password}` → `{accessToken}` + cookie (the backend auto-logs-in the new user — no `UserDto` anymore); `POST /auth/refresh` **no body** (public, cookie-authenticated) → `{accessToken}` + rotated cookie — rotation deletes the old refresh token server-side, so replaying it 401s (the failed refresh also clears the cookie); `POST /auth/logout` **no body** (JWT-protected; the cookie identifies the token to revoke, which the server also clears); `POST /auth/forgot-password` `{email}`; `POST /auth/change-password` `{oldPassword, newPassword}` (revokes all refresh tokens and clears the cookie); `GET /auth/hello` (plain text). All `/auth/*` requests are sent `withCredentials` so the cookie flows cross-origin.
- **Users** (`UserService`, ADMIN-only): non-paged `GET` list, `PATCH /{id}/status`, `PATCH /{id}/role`, `DELETE /{id}`. (`GET /users/current-user` is the one user-scoped exception — feeds the `/user-setting` page.)
- **Images** (`UserImageService`, owner-scoped, MinIO-backed): `POST /images/avatar` multipart field `file` (png/jpeg/webp, ≤5MB; never set a Content-Type header — HttpClient derives the multipart boundary) → `UserImageDTO {id, contentType, fileSize}` (frontend: `model/user-image.model.ts`). `GET /images/avatar` streams the bytes with the stored Content-Type — it needs the JWT header, so it can never be a plain `<img src>`: fetched as a Blob and published via `AuthService.setAvatarUrl()` as a `blob:` object URL (never persisted to localStorage — blob URLs die with the document). `DELETE /images/avatar` → `MessageResponse` (the misspelled `messag` key again); 404 on GET/DELETE when none is uploaded.
- **PDF files** (`UserPdfFileService`, owner-scoped, MinIO bucket `app.minio.pdf-bucket=user-pdf-files`): `POST /pdf-files` multipart with the **repeated field `files`** — 1–10 PDFs per request, 20MB each (client mirrors the limits; one request = one rate-limit slot) → `201` plain `List<UserPdfFileDTO>` `{id, fileName, contentType, fileSize, createdAt}` (`model/user-pdf-file.model.ts`; `fileName` is the sanitized original, the MinIO key never leaves the server). `GET /pdf-files?page&size` → `PagedResponseDTO` sorted `createdAt` DESC. `GET /pdf-files/{id}` streams `application/pdf` with a `Content-Disposition: attachment` — JWT-needed, so downloads are Blobs saved via a temp `<a download>` with the object URL revoked right after (avatar precedent). `DELETE /pdf-files/{id}` → `MessageResponse`. Multipart servlet caps are 21MB/220MB; an over-cap request gets a 400 whose message names the tripped limit (`MaxUploadSizeExceededException` handler).
- **Notifications** (`NotificationService`, WebSocket push — not REST): raw WebSocket at `ws://…/ws/notifications?token=<accessJWT>` (URL derived from `environment.apiUrl` with `http`→`ws`; the browser WebSocket API can't set headers, so the access token rides the query string and a backend handshake interceptor validates it). Server broadcasts one JSON text frame to every connected client every 30 min (`app.notification.interval-ms`): `Notification {message: string, timestamp: string}` — `timestamp` is ISO-8601 UTC, validated client-side with `Date.parse` before storing. Handshake auth is one-time; on reconnect the service refreshes first if the 15-min token expired.
- **Meetings** (`MeetingService` / `MeetingParticipantService` / `MeetingChatService`, JWT-protected; `model/meeting.model.ts`): the meeting control plane. Two id kinds: participant-facing paths address the **10-char `joinCode`**; only the lifecycle transitions `PATCH /meetings/{id}/start|cancel|end` take the **internal numeric id** (the `/my` list rows are where the UI has it). Authorization is per-meeting participant role (HOST/COHOST/PARTICIPANT via the backend's `MeetingAuthority`), not the account role.
  - `POST /meetings` `CreateMeetingRequest` → `201 MeetingDTO`. Validation is manual server-side (400): title required; SCHEDULED requires both `scheduledStartAt`/`scheduledEndAt` with end after start; INSTANT must not carry timestamps; optional `password` trims to 4–100 chars (blank = open meeting, stored BCrypt-hashed). INSTANT create returns the host's `media`; SCHEDULED leaves the host participant `LEFT` until `start`. `MeetingDTO.hasPassword` (never the hash) tells clients to prompt at join.
  - `GET /meetings/my?page&size` → paged `MeetingDTO` — **hosted meetings only** (`findByHostId`), `media` always null. `GET /meetings/{joinCode}` → summary `MeetingDTO` (404 unknown).
  - Hosts never call join: INSTANT create (or `start`, which returns host `media`) already seats them JOINED — the UI navigates straight into the room.
  - Under `/meetings/{joinCode}`: `POST /join` body `{password: string|null}` → `MyMeetingStatusDTO` (`media` present iff JOINED + IN_PROGRESS; 409 unless IN_PROGRESS and unlocked). **Password-protected meetings 403 non-host callers without the correct password** — 403, never 401 (the interceptor owns auth-death 401s); the host account is exempt and the gate covers rejoins. The room's `join(password?)` prompts via the join-password modal when `hasPassword` and re-opens it on a 403 with the server message. `GET /me` → the same DTO — the **polling channel** (`participant` null = never touched; `media` appearing is the waiting-room admit signal); `POST /leave` → `messag` ack. Join-state rules: never-joined → WAITING (auto-JOINED when the waiting room is off); LEFT/DECLINED rejoin straight to JOINED; REMOVED/DENIED are forced back to WAITING.
  - Moderation (HOST/COHOST unless noted): `GET /lobby`, `POST /lobby/{userId}/admit|deny`, `GET /roster`, `PATCH /participants/{userId}/mute` (the host row is 409), `DELETE /participants/{userId}` (host 409; COHOST removing COHOST is 403), `PATCH /participants/{userId}/role` `{role: COHOST|PARTICIPANT}` (HOST only, host rows 409), `PATCH /lock` `{locked}` (HOST only — locking stops minting media tokens). Self: `PATCH /participants/me/mute`, `PATCH /participants/me/speaking` `{speaking}` (local mic-analysis flag; the server clamps it to false while muted — `SpeechDetectionService` supplies it, throttled to ≥1.5 s between PATCHes; `ParticipantDTO.speaking`/`lastSpeakingAt` ride the roster poll and drive the stage indicator + adjacency ordering).
  - Chat `GET /meetings/{joinCode}/chat?page&size` → paged `ChatMessageDTO` sorted `sentAt DESC, id DESC` (the store reverses pages for ascending display); readable by any past-or-present participant incl. after the meeting ends — **each viewer sees broadcasts plus only their own private traffic**. `POST` body `{content, recipientUserId}` (201, content ≤2000 chars, JOINED + IN_PROGRESS only; a `recipientUserId` makes it private, 400 for self/non-participant targets; `recipientId`/`recipientName` mirror back on the DTO), `DELETE /{messageId}` (author or HOST, idempotent).
  - `MediaCredentialsDTO {liveKitUrl, liveKitToken, janusWsUrl, janusRoomId, janusPin, muted}`: the LiveKit token TTL is **5 minutes** and every `/me` poll re-mints it — never cache it; `janusRoomId` equals the meeting's internal id. No WebRTC SDK is wired yet (the room shows a connection-info panel); `environment.ts` deliberately carries no `liveKitUrl`/`janusWsUrl` copies — the DTO is the single source of truth until that milestone.
  - `POST /webhooks/livekit` is server-to-server (LiveKit-signed) — the frontend never calls it.
  - Polling budget: `MeetingRoomService` polls `/me` every 2 s, the **roster every 2.5 s** (the speaking flag rides it, so the cadence bounds indicator lag), and a sequential lobby → chat-reconcile chain every 5 s while joined (≈1.4 req/s + throttled speaking PATCHes, under the 3 req/s cap); 429/network errors back the `/me` loop off to 10 s, 404/401 and terminal states (meeting ENDED/CANCELLED, participant REMOVED/DENIED) stop it, and `join()` restarts it. Two tabs of one account share the budget — expect occasional 429s there (secondary chains are best-effort).
- **Pagination**: list endpoints return `PagedResponseDTO {content, page, size, totalElements, totalPages, first, last}` (frontend: `model/paged-response.model.ts`, with `PageParams {page?, size?}`).
- **Error bodies come in three shapes** — the global handler's `{status, message, timeStamp}`, the hand-rolled `{"messag": "..."}` (key really is misspelled on the backend; do not "fix" the frontend mirror), and bare strings. `util/api-util.ts` `getApiErrorMessage()` normalizes all three.
- **Rate limiting**: any endpoint can answer **429** (shape one + a `Retry-After: 1` header) when a client exceeds ~3 requests/second — the budget is per JWT subject, or per IP for unauthenticated calls (`app.rate-limit.requests-per-second` on the backend). The interceptor only retries 401s, so 429s surface to the caller as-is and flow through `getApiErrorMessage()` unchanged; page loads firing parallel GETs can legitimately trip it (two tabs share one budget).
- **JWT**: claims are `{sub: email, role, iat, exp, typ: 'access'}`; roles are `ROLE_USER | ROLE_ADMIN | ROLE_CUSTOMER`. Access tokens live **15 minutes** and are stored memory-only client-side (never localStorage); the opaque 64-hex refresh token (7-day server-side expiry) lives exclusively in the HttpOnly `asset-manager.refreshToken` cookie (`SameSite=Strict`, `Path=/auth` — invisible to JS, so the client learns session state only by attempting a refresh). Expired/invalid Bearer headers get a clean 401 `ErrorResponseDTO` (even on public endpoints) — hence the interceptor only attaches live tokens and refreshes proactively (see `architecture.md`).
