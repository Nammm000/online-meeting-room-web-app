# MinIO in the Backend

MinIO is the S3-compatible object store used for **user avatars** — the only feature that touches it. Two classes import the MinIO SDK: `configuration/MinioConfiguration` (client bean + bucket bootstrap) and `services/image/UserImageService` (all put/get/remove calls).

The split of responsibilities:

- **PostgreSQL** stores the *pointer*: an `images`/`user_image` row with `objectKey`, `contentType`, and `fileSize` (one row per user, enforced by a unique `user_id`).
- **MinIO** stores the *bytes*: the image object in bucket `user-images` under key `avatars/<userId>/<uuid>.<ext>`.

The browser never talks to MinIO — there are no presigned URLs and no publicly exposed endpoints. All three REST endpoints stream the bytes through the backend:

```
browser ──JWT──> Angular/React frontend ──> backend :8083 /images/avatar
                                                │  UserImageService
                                                │  ├─ userImageRepo (pointer row)
                                                ▼
                                          MinioClient ──S3 API──> MinIO :9000
                                                                     bucket "user-images"
                                                                     object "avatars/<userId>/<uuid>.<ext>"
```

## 1. Infrastructure (docker-compose.yml)

```yaml
minio:
  image: quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z   # pinned; MinIO left Docker Hub
  command: server /data --console-address ":9001"
  environment:
    MINIO_ROOT_USER: minioadmin
    MINIO_ROOT_PASSWORD: minioadmin
  ports: ["9002:9000", "9003:9001"]
  volumes: [minio_data:/data]
  healthcheck: curl -f http://localhost:9000/minio/health/live
```

- **9000** = S3 API (what `MinioClient` talks to), **9001** = web console (browse buckets at http://localhost:9001, login `minioadmin`/`minioadmin`).
- Data persists in the `minio_data` named volume.
- There are **no init scripts or `mc` sidecars** — the `user-images` bucket is created by the app itself at startup (below), so `docker compose up -d` alone leaves MinIO empty until the backend boots.

## 2. Application configuration

`application.properties`:

| Property | Value | Purpose |
|---|---|---|
| `app.minio.endpoint` | `http://localhost:9000` | S3 API endpoint the client points at |
| `app.minio.access-key` / `app.minio.secret-key` | `minioadmin` / `minioadmin` | Root credentials (dev defaults) |
| `app.minio.bucket` | `user-images` | Bucket for avatar objects; injected into `UserImageService` |
| `spring.servlet.multipart.max-file-size` | `6MB` | Multipart cap, deliberately **above** the 5MB avatar limit |
| `spring.servlet.multipart.max-request-size` | `6MB` | Whole-request cap (same reasoning) |

`configuration/MinioConfiguration` builds the single `MinioClient` bean (endpoint + credentials, no region — fine for a local single-node MinIO) and then runs `bootstrapBucket`: `bucketExists(bucket)` → `makeBucket` if absent, logging `Created MinIO bucket 'user-images'`.

> **Startup is a hard dependency.** Bootstrap runs eagerly inside the `@Bean` method. If MinIO is unreachable, the bean throws `IllegalStateException` and the whole Spring context fails to build — the app does not start without MinIO.

## 3. Data model

`models/image/Image` — abstract `@Entity`, `images` table, JOINED inheritance (mirrors the `Asset` pattern):

| Field | Column | Notes |
|---|---|---|
| `id` | `id` | Identity PK, shared with the subclass table |
| `user` | `user_id` | `@OneToOne`, not null, **unique** → DB-enforced one avatar per user |
| `objectKey` | `object_key` | varchar(500), the MinIO object path |
| `contentType` | `content_type` | varchar(100), full MIME (`image/png`, …) |
| `fileSize` | `file_size` | bytes, max 5 MB by service rule |

`models/image/UserImage` (`user_image` table) adds `imageType` (enum, single value `AVATAR`), force-set by `@PrePersist`. The relation is unidirectional — `User` has no back-reference. Schema is generated by `spring.jpa.hibernate.ddl-auto=update` like everything else.

`repo/UserImageRepo`: `findByUserId(Long)` (drives every operation) and `existsByUserId` (currently unused).

## 4. API surface — `/images` (`UserImageController`)

All three endpoints require a JWT (nothing under `/images/**` is in the permitAll list). Scoping is implicit: each service method resolves `UserUtils.getCurrentUser()` and looks up `findByUserId(user.getId())` — no user id is ever accepted from the request.

| Method | Endpoint | Request | Response |
|---|---|---|---|
| POST | `/images/avatar` | multipart, part name **`file`** | 200 + `UserImageDTO {id, contentType, fileSize}` |
| GET | `/images/avatar` | — | 200, raw bytes with the stored Content-Type and `Cache-Control: no-cache`; 404 if none |
| DELETE | `/images/avatar` | — | 200, body `{"messag":"Avatar deleted successfully"}` (the key typo is real — `MeetingRoomUtils.getResponseEntity` builds it by string concat) |

`Cache-Control: no-cache` because upload *replaces* the avatar in place: the client must revalidate instead of caching stale bytes.

## 5. API flows

### Upload / replace — `POST /images/avatar` → `UserImageService.uploadAvatar`

1. **Validate** (`validateImage`, client-declared `file.getContentType()`, not sniffed):
   - null/empty → `IllegalArgumentException("Image cannot be empty")`
   - size > 5 MB → `"Image must be smaller than 5MB"`
   - MIME not in `{image/png, image/jpeg, image/webp}` → `"Only png, jpeg and webp images are allowed"`
2. Resolve the current user from the JWT.
3. Build the object key: `avatars/<userId>/<uuid>.<ext>` — the extension comes from a MIME→ext map (`image/jpeg` → `.jpg`); **the client filename is never used**, so a hostile name can't influence storage paths.
4. `putObject` the new object (streams the multipart file with known size).
5. If a row already exists → best-effort `removeObject` of the **old** key (failure is only `log.warn`'d, leaving an orphaned object).
6. Upsert the row (existing row updated, else new one created) and return `UserImageDTO` (manual mapping, no MapStruct).

Two-tier size limit: requests **over 6MB** are rejected by the multipart cap first (`MaxUploadSizeExceededException` → 400 "Image must be smaller than 5MB"); files between 5–6 MB make it into the service and fail validation with the same clear message.

### Download — `GET /images/avatar` → `getAvatar`

1. Resolve current user, `findByUserId` → `NotFoundException("No avatar uploaded")` → **404** if absent.
2. `getObject` from MinIO, `readAllBytes()` into memory.
3. Controller returns the bytes with the **stored** Content-Type (so a webp stays webp regardless of request headers) and `no-cache`.

### Delete — `DELETE /images/avatar` → `deleteAvatar`

1. Resolve row, else 404 as above.
2. Delete the DB row **first**.
3. Best-effort `removeObject`; on failure just warn.

Ordering rationale: the acceptable failure mode is an **orphaned object** in MinIO (invisible, wasted space), never a DB row pointing at bytes that no longer exist (which would 400 on every subsequent GET).

### Startup — `MinioConfiguration.bootstrapBucket`

`bucketExists` → `makeBucket` when missing → app ready. Any SDK error → `IllegalStateException`, context refuses to start.

## 6. Error mapping

The service never lets a raw MinIO SDK exception (`ErrorResponseException`, `InsufficientDataException`, `XmlParserException`, …) escape — `putObject`/`getObject` catch `Exception` and wrap in `IllegalStateException("Failed to store/read image …")`; `removeObject` swallows entirely. `AllExceptionHandler` then renders:

| Failure | Exception | HTTP |
|---|---|---|
| Validation (empty / >5MB / bad type) | `IllegalArgumentException` | 400 (catch-all) |
| No avatar on GET/DELETE | `NotFoundException` | 404 |
| Request >6MB multipart cap | `MaxUploadSizeExceededException` | 400, message "Image must be smaller than 5MB" |
| MinIO put/get failure (incl. outage) | wrapped `IllegalStateException` | **400 via the catch-all — not 500** |
| Missing/invalid JWT | `JwtRequestFilter` | 401 |

Error body is always `ErrorResponseDTO {statusCode, message, timestamp (epoch millis)}`.

## 7. Caveats & non-obvious behavior

- **No `@Transactional`** in `UserImageService`: the object write and the row write are not atomic. Upload order is put-new → remove-old → save row; if the row save fails after the old object was removed, the row points at a deleted key. A failed old-object removal just orphans an object.
- **Storage outages look like client errors** (400) because the wrapped `IllegalStateException` falls through to the catch-all — arguably these should be 5xx.
- **Content-Type is trusted from the client**; the stored extension is derived from that declared MIME.
- **Whole file in memory**: uploads stream with known size, but downloads `readAllBytes()` into a `byte[]` — fine at the 5MB cap, just not streaming.
- `existsByUserId` is dead code, and `MeetingRoomUtils.getResponseEntity` returns the misspelled `messag` key shown above.

## Quick manual check

```bash
docker compose up -d                 # MinIO on :9000, console on :9001
mvn spring-boot:run                  # bucket "user-images" appears at startup
# then, with $TOKEN from /auth/login:
curl -F "file=@me.png;type=image/png" -H "Authorization: Bearer $TOKEN" http://localhost:8083/images/avatar
curl -H "Authorization: Bearer $TOKEN" http://localhost:8083/images/avatar -o me.png
curl -X DELETE -H "Authorization: Bearer $TOKEN" http://localhost:8083/images/avatar
```
