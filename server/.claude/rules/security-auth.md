# Security & Authentication

Stateless JWT auth (jjwt 0.11.5, hardcoded secret in `util/JwtUtil`) with DB-persisted refresh tokens:

- Access token: 15-min JWT (expiry in `constants/AuthConstants`) with `role` + `typ=access` claims. `JwtRequestFilter` (OncePerRequestFilter) extracts/validates the Bearer token, rejects expired/malformed/non-access tokens by writing a 401 `ErrorResponseDTO`-shaped JSON (plus `WWW-Authenticate: Bearer`) directly to the response, loads the user via `UserDetailsServiceImpl`, and populates the SecurityContext before `UsernamePasswordAuthenticationFilter`.
- Refresh token: opaque 64-char secure-random string stored in the `refresh_tokens` table (`models/RefreshToken`, 7-day expiry, unique token column, FK to `users`). It is delivered exclusively as the HttpOnly cookie `asset-manager.refreshToken` (`RefreshCookieService`: `HttpOnly; SameSite=Strict; Path=/auth; Max-Age=7d`, `Secure` via `app.cookie.secure` property, default false for http dev) — never in a response body, so JS can never read it. `RefreshTokenService` issues, rotates (`POST /auth/refresh` reads the cookie, deletes the presented token, sets a fresh cookie, returns `TokenPair` → only `{accessToken}` in the body — replaying a used token → 401 `InvalidTokenException`), and revokes (logout deletes the cookie's token; change-password deletes all). A failed refresh also clears the cookie. There is no `refreshTokens` collection on `User` — deletion goes through bulk JPQL in `RefreshTokenRepo`. CSRF: `SameSite=Strict` + `Path=/auth` is the mitigation (refresh is the only purely cookie endpoint and rotation neutralizes a CSRF'd refresh; logout/change-password also require the Bearer header).
- `WebSecurityConfiguration` permits `/auth/login`, `/auth/signup`, `/auth/refresh`, `/auth/forgot-password`, `/auth/hello`, plus eight dead `/dashboard`/`/news`/`/plan` routes that have no controllers behind them (known issue — `project-overview.md`); everything else requires authentication. `/ws/**` is also `permitAll` — NOT because the WebSocket is public: the browser WebSocket API cannot set an `Authorization` header on the handshake GET, so the real gate is `websocket/WebSocketAuthInterceptor`, which validates the access token passed as a `?token=` query param through the same JwtUtil sequence as `JwtRequestFilter` (extract username → `typ=access` → UserDetails → signature/expiry) and rejects with 401; `WebSocketConfiguration` enforces the `Origin` header via `setAllowedOrigins(app.client.url)` (the WS equivalent of CORS). Accepted trade-off: the JWT appears in the handshake query string. CORS is a single `CorsConfigurationSource` bean wired via `.cors(withDefaults())` consuming `app.client.url` — `allowCredentials(true)` with exact origins (mandatory for the credentialed cross-origin cookie). The old `SimpleCorsFilter` (echoed any origin, no `Allow-Credentials`) and the app-level `CorsFilter` bean are deleted.
- Rate limiting: `filters/RateLimitFilter` (OncePerRequestFilter) runs directly after `JwtRequestFilter` (`.addFilterAfter(rateLimitFilter, JwtRequestFilter.class)`) and must stay inside the security chain — the JWT filter clears the SecurityContext in a `finally` once the chain returns, so a plain servlet filter outside the chain would never see the identity. It caps each client at `app.rate-limit.requests-per-second` (default 3) per rolling second via `util/SlidingWindowRateLimiter`: an in-memory sliding-window log (`ConcurrentHashMap<String, ArrayDeque<Long>>`, per-key `synchronized`; rejected requests log no timestamp, so hammering the API cannot extend the block; a `@Scheduled` 5-min sweep evicts idle keys). Keys are `user:<email>` (JWT subject) once authenticated, else `ip:<remoteAddr>` — `X-Forwarded-For` is deliberately ignored (no trusted proxy in front; revisit if that changes, since a proxy would collapse every client into one IP). OPTIONS preflights are exempt (`shouldNotFilter`); `/ws/**` costs one IP-bucket slot per handshake GET (WS frames bypass the chain). Excess requests get a hand-written 429 `ErrorResponseDTO`-shaped JSON + `Retry-After` header (seconds, min 1), mirroring `JwtRequestFilter`'s 401 pattern — CORS headers are already on the response because the CorsFilter runs earlier in the chain.
- Method-level auth via `@EnableMethodSecurity` and `@PreAuthorize("hasRole('ADMIN')")` on admin endpoints (user management — the only `@PreAuthorize` surface in the codebase).
- Per-resource authorization happens in services: `UserUtils.checkOwnership(pdfFile)` — the only overload, called from `UserPdfFileService` — throws `AccessDeniedException` (→ 403) when the file belongs to another user; `ROLE_ADMIN` bypasses the check. The request-scoped identity behind `UserUtils` is `configuration/RequestSecurityContext`, populated by `JwtRequestFilter`.
- Login flow: `AuthenticationController.login` authenticates against Spring Security, then `JwtUtil.generateToken(username, role)` embeds the role as a claim and `RefreshTokenService.createToken(user)` persists a refresh token; login, signup, and refresh all return `AuthenticationResponse {accessToken}` and set the refresh cookie on the response.
